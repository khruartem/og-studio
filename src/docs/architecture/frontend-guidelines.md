# Frontend Guidelines

> Внутренние соглашения проекта.
>
> Цель документа — сделать кодовую базу единообразной, предсказуемой и удобной для поддержки.

---

# Основные принципы

При проектировании компонентов придерживаемся следующих принципов:

- один компонент — одна ответственность;
- композиция предпочтительнее наследования;
- API компонента важнее внутренней реализации;
- простые решения предпочтительнее сложных;
- читаемость важнее краткости.

---

# Структура компонентов

Каждый компонент должен решать одну задачу.

Хорошо:

```
Logo
Menu
MenuItem
Socials
Button
Section
```

Плохо:

```
HeaderNavigationMenuSocials
```

Если компонент начинает выполнять несколько независимых задач — его следует разделить.

---

# Композиция

Предпочитаем композицию компонентов.

Например:

```
Header
│
├── Logo
├── Menu
├── Button
└── MobileMenu
```

вместо одного большого компонента.

---

# API компонентов

Каждый компонент должен иметь небольшое и понятное API.

Хорошо:

```astro
<Logo variant="light" />

<Menu items={navigation} />

<Button size="lg" />
```

Плохо:

```astro
<Logo
    white
    textWhite
    markPurple
    hoverDark
/>
```

---

# Props

Используем интерфейс Props.

```ts
interface Props {
    class?: string;
}
```

Получаем пропсы через

```ts
const { class: className = "" } =
    Astro.props as Props;
```

Используем `className`, чтобы не конфликтовать с ключевым словом `class`.

---

# TypeScript

Используем строгую типизацию.

Предпочитаем

```ts
instanceof
```

вместо

```ts
as HTMLButtonElement
```

если существует возможность проверить тип во время выполнения.

---

# Разделение ответственности

Разметка не должна содержать бизнес-логику.

Например

```
MobileMenu.astro
```

отвечает только за структуру.

Вся логика открытия находится в

```
createMobileMenu.ts
```

---

# Контроллеры

Если компонент имеет поведение,
создаем отдельный контроллер.

```
MobileMenu
│
├── MobileMenu.astro
└── createMobileMenu.ts
```

Контроллер самостоятельно управляет состоянием компонента.

---

# Работа с DOM

Поиск DOM-элементов выполняется внутри контроллера.

Не дублируем

```ts
querySelector(...)
```

в нескольких местах.

---

# Data Attributes

Используем `data-*` только для хранения состояния компонента.

Например:

```html
data-state="open"
```

или

```html
data-state="closed"
```

Не используем `data-*`,
если достаточно обычного класса.

---

# Accessibility

Все интерактивные элементы должны быть доступны.

Обязательно используем:

```
aria-expanded
aria-controls
aria-label
```

если они необходимы.

Кнопки всегда имеют

```html
type="button"
```

---

# SVG

Все обычные иконки используют

```svg
fill="currentColor"
```

Цвет задается через Tailwind.

Например

```astro
<Arrow class="text-pulse" />
```

---

Логотипы являются исключением.

Для них используем CSS-переменные.

Например

```css
--logo-text-color
--logo-mark-color
```

---

# Tailwind

Tailwind используется для:

- layout;
- spacing;
- typography;
- размеры;
- цвета;
- flex/grid.

Локальный CSS используется:

- для сложных состояний;
- анимаций;
- псевдоэлементов;
- длинных селекторов;
- когда utility-классы ухудшают читаемость.

---

# Семантические цвета

Не используем HEX внутри компонентов.

Плохо

```css
color: #C72FCB;
```

Хорошо

```css
color: var(--color-pulse);
```

или

```astro
class="text-pulse"
```

---

# Данные

Если компонент отображает коллекцию,
данные выносятся отдельно.

Например

```
navigation.ts
socials.ts
```

Компонент отвечает только за отображение.

---

# Компоненты

Предпочитаем маленькие компоненты.

Например

```
Menu
│
└── MenuItem

Socials
│
└── SocialLink
```

вместо большого универсального компонента.

---

# Именование

Используем понятные имена.

Хорошо

```
createMobileMenu
getCurrentYear
navigation
```

Плохо

```
utils
helpers
common
misc
```

---

# Структура проекта

Компоненты располагаются по предметной области.

```
components/

navigation/

layout/

ui/
```

а не по типу файлов.

---

# Производительность

Не добавляем JavaScript,
если задачу можно решить HTML или CSS.

Каждый новый скрипт должен быть оправдан.

---

# Перед созданием нового компонента

Задаем себе вопросы:

- Выполняет ли компонент одну задачу?
- Можно ли переиспользовать его?
- Понятно ли его API?
- Не знает ли он слишком много?
- Можно ли упростить решение?
